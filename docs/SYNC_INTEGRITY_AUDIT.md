# Синхронизация: функциональная проверка и границы

Это аудит действующей логики синхронизации. Изменения оформления сюда не входят. Предыдущие установщики не считаются сборками новых исправлений до повторной упаковки.

## Исправленные сценарии

- Передача Desktop больше не удаляет очередь. Сохраняются порядок, повторные вхождения трека, выбранный queueIndex, позиция, playing, shuffle и repeat. Любой только локальный элемент останавливает передачу всей очереди с понятным объяснением; файлы автоматически не загружаются. Получение сначала разрешает все файлы и лишь затем передаёт готовое состояние проигрывателю.
- Состояние содержит настройки восьми тем и визуализаций, качества, FPS, интенсивности, отключения анимаций/фона и advanced mode. Неизвестные поля другого клиента сохраняются. Неподдерживаемые удалённые значения не затирают пригодные локальные настройки.
- Серверная история принимает стабильный eventId и исходный playedAt. Повтор после потерянного HTTP-подтверждения возвращает то же событие; другой payload с этим ключом получает 409. Desktop хранит стабильный ID устройства, формирует ключ на локальное событие и сохраняет исходную дату. Времена нормализуются до микросекунд.
- Импорт события на ПК и отметки «получено/уже отправлено» записываются одной SQLite-транзакцией. Повторное получение после перезапуска не создаёт дубликат.
- При подтверждении отправки Desktop сначала сохраняет отметку получения серверного события, затем отправки исходной строки. Если вторая запись не удалась, повтор использует тот же eventId; получение не дублирует собственное событие. Этот промежуток проверен настоящим отказом SQLite-записи через trigger.
- Плейлисты имеют version. Устаревший PUT с version не перезаписывает чужое изменение. Desktop сохраняет базовую версию/снимок; при конфликте отправки создаёт отдельную копию, сохраняя обе версии. При получении несохранённые локальные изменения также сохраняются отдельным локальным плейлистом. Замена локального содержимого выполняется одной транзакцией.
- Избранное сопоставляется с сохранённым базовым состоянием. Нетронутый кэш ПК не удаляет новый лайк с телефона. При первом обмене существующие лайки объединяются. Неотправленное локальное изменение сохраняется при получении серверной коллекции. Удалённые с сервера файлы не приводят к удалению их локальных копий/метаданных.
- Изменения локальной коллекции уведомляют основной экран через onLibraryChanged на JavaFX-потоке; кэш медиатеки и навигация перечитываются.
- Папочный импорт разрешён только явно заданному неизменяемому ID аккаунта. Непроверенный email не выдаёт права; удаление аккаунта и повторная регистрация с тем же email не возвращают доступ. Старый параметр IMPORT_ADMIN_EMAIL не действует.

Обратная совместимость: клиенты без eventId/playlist version остаются работоспособными, но для них не обещаются дедупликация повторной отправки и защита устаревшего редактирования плейлиста. Миграция V2 добавляет уникальный ключ истории и version, не удаляя существующие данные.

## Что проверено сейчас

После этих изменений выполнены:

- backend/server: 18 тестов без ошибок, включая сохранение исходной даты и idempotent retry, stale playlist version → 409 без изменения содержимого, очередь с повторным треком и проверкой выбранного индекса, неизменяемый ID администратора импорта и настоящие встроенные PNG/JPEG обложки;
- выбранный набор core/Desktop: 8 core/lyrics тестов и 11 HTTP/queue тестов без ошибок. Включены атомарный импорт истории после reopen и откат некорректного обновления плейлиста, полный round-trip очереди между разными ID устройств, объяснение только локального трека и отказ от недоступного элемента;
- настоящий собранный сервер H2/Flyway и настоящие Desktop ServerClient/SQLite-библиотеки прошли 23 новых HTTP-сценария: [verification/sync-http.json](verification/sync-http.json). Проверены очередь A/B/A с индексом 2, файлы с одинаковым SHA-256 на обоих устройствах, позиция/режимы и визуальные настройки, сохранение неизвестных полей, повтор истории после потерянного подтверждения, отказа SQLite-маркера и перезапуска, конфликт плейлиста, согласование лайков и сохранение локальной копии после серверного удаления. Файловая база успешно обновлена с V1 до V2;
- повторный основной HTTP-проход новой сборки: ещё 21 PASS, включая Range206, авторизацию и изоляцию: [verification/server-http.json](verification/server-http.json).

## Явные ограничения

Операция «Коллекция» состоит из запросов к нескольким ресурсам: это не общая распределённая транзакция. Прерывание может оставить частично завершённую передачу; история с eventId, повторные favorites и версионные записи безопасны для повторения. Создание нового плейлиста пока не имеет отдельного ключа идемпотентности: потеря подтверждения POST может создать вторую копию при повторе.

Локальный плейлист хранит один экземпляр трека; серверный плейлист и очередь проигрывателя допускают повторы. Неизменённый локальный снимок не отправляется поверх серверного и не удаляет его повторные ссылки. История импортируется только для треков, уже доступных в локальной библиотеке; её отсутствие не вызывает неявное скачивание аудио. Desktop перебирает до 100000 локальных событий, серверную историю читает страницами по 1000.

Нет push/WebSocket и общей модели tombstones для удаления: локальное удаление плейлиста/истории не рассылается всем устройствам автоматически. Старый офлайн-клиент может прислать ранее не переданное событие после серверной очистки истории. Избранное использует сопоставление состояний, а не журнал всех отдельных переключений.

PostgreSQL runtime, Docker/HTTPS и аппаратные сценарии телефона пока требуют отдельной проверки. Настоящая проверка HTTP на H2 не подтверждает установку/фоновые режимы Android или iOS. Автоматизированные сценарии частной ServerView-кнопки создания копии плейлиста при конфликте отдельно не запускались; контракт 409 и атомарная замена локального содержимого проверены.
