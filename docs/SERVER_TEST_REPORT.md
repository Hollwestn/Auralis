# Проверка Backend и Desktop HTTP

Обновлено: 18 октября 2026 года. Среда: Windows 11, Oracle JDK 25.0.3, Maven 3.9.16, FFmpeg N-119884-gfb65ecbc9b-20250614. Никаких личных музыкальных файлов для тестов не использовано: fixtures — синусоидальные WAV и небольшие встроенные PNG/JPEG, созданные локально для проверки.

## Полная Java-сборка

Фактически выполнено из корня:

```powershell
mvn -B -ntp verify '-Dmaven.repo.local=C:/Users/пк/.m2/repository'
```

Первый проход 17 октября: BUILD SUCCESS, 29 тестов. После изменений 18 октября полный verify прошёл 44 теста (8 core, 18 Desktop, 18 backend). Серверный набор: 6 ByteRange, 1 сценарий выдачи прав импорта, 11 Spring Boot/H2 интеграций. Последующая проверка RIFF INFO + ID3 повторно прошла все 11 интеграций, после изменения порядка маркеров истории повторно прошли 11 Desktop HTTP/queue тестов и сквозной fault-injection ниже. Последний общий счёт сверяется в TEST_REPORT.md и Surefire; результаты разных прогонов здесь не суммируются. Собраны настоящий Desktop JAR и самостоятельный Spring Boot JAR.

Backend-тесты проверяют пустую БД, миграцию Flyway, PBKDF2-авторизацию и logout, изоляцию каталога, реальную загрузку WAV и побайтовый Range, дедупликацию, отклонение ложного MP3/отключённого импорта, плейлисты/избранное/историю, запрет чужих ID в sync, конфликт версии и влияние предпочтений/DISLIKE на рекомендации. Новые проверки покрывают исходную дату и идемпотентность истории, stale playlist version → 409, полный индекс очереди с повторами, импорт только по неизменяемому ID (включая повторную регистрацию email после удаления), настоящие встроенные PNG/JPEG, MIME/байты/частный кэш/401/404, ленивое извлечение и очистку обложек, отклонение SVG и слишком широкого изображения.

Desktop HTTP-тесты используют настоящий HTTP по loopback и проверяют bearer заголовок, streaming multipart с исходными байтами, JSON ошибки и статус 409, запрет стороннего origin/выхода из API, запрет перехода по редиректу, скачивание через временный файл и сохранение старой копии при ошибке.

## Настоящий сервер и настоящий Desktop ServerClient

После verify запущен собранный сервер:

```powershell
java -jar backend/server/target/auralis-server-0.1.0-SNAPSHOT.jar --spring.profiles.active=dev --server.port=18080 '--spring.datasource.url=jdbc:h2:file:./.runtime/server-smoke/nio2;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE' --auralis.storage=./.runtime/server-smoke/music
```

Реально получен Started AuralisServer / Tomcat NIO2 на 127.0.0.1:18080. GET health вернул ok. Временный Java harness использовал **скомпилированный Desktop ServerClient**, две сессии одного аккаунта (ПК и второе устройство) и отдельный чужой аккаунт. Это проверка общей HTTP-интеграции; физический телефон в ней не участвовал.

21 проверка PASS:

1. Регистрация и приватный пустой каталог.
2. Передача настоящего WAV и чтение размера/длительности.
3. SHA-256 дедупликация повторной передачи.
4. Вход второй сессии и общий каталог.
5. Избранное между сессиями.
6. Плейлист с сохранённым порядком, включая повторную ссылку.
7. История между сессиями.
8. Персональная волна с объяснениями.
9. Продолжение позиции и темы на второй сессии.
10. HTTP 409 при устаревшей версии.
11. Повторное чтение и успешная запись после конфликта.
12. Скачанный WAV побайтово идентичен оригиналу (совпадение SHA-256).
13. HTTP 206, Content-Range и правильные байты 1000–1999.
14. Пустой каталог чужого аккаунта.
15. Чужой trackId получает 404.
16. Анонимный каталог получает 401.
17. Неверный пароль получает 401.
18. DISLIKE исключает трек из волны.
19. Очистка истории видна второй сессии.
20. Удаление аккаунта отзывает токены обеих сессий.
21. Настоящий /openapi.json возвращает OpenAPI 3.0.3.

Машиночитаемые доказательства: [verification/server-http.json](verification/server-http.json), включая время, размер и оба SHA-256. Токены/пароли в отчёт не записывались. Тестовые аккаунты и серверные аудиокопии удалены через API в finally. Fixture и скачанная проверочная копия находятся в `.runtime/` для QA; синтезированная музыка не поставляется в docs. Тестовый сервер после проверки остановлен.

## Дополнительная синхронизация и настоящие обложки, 18 октября

Ещё 23 сквозных сценария использовали настоящий Desktop ServerClient, две отдельные локальные SQLite-библиотеки, реальные FFmpeg-импорты и серверную файловую H2, обновлённую с V1 до V2. Проверены A/B/A с queueIndex=2 и режимами воспроизведения, оба SHA-256 после скачивания, новые визуальные настройки и неизвестные поля, согласование избранного с другого устройства, eventId при потерянном подтверждении, исходная дата и идемпотентность после reopen, 409 плейлиста и сохранение локального файла после серверного удаления. Отдельно SQLite-trigger намеренно прерывает запись historySent после подтверждения HTTP: получение не создаёт повтор собственной строки, повторная отправка сохраняет одно серверное событие. Доказательства: [verification/sync-http.json](verification/sync-http.json).

Отдельный собранный сервер на loopback18081 прошёл 13 HTTP-проверок обложек. Настоящие PNG и JPEG встроены в WAV-теги, явно загружены через Desktop-клиент и получены через защищённый endpoint. Проверены точное равенство исходных байтов, Content-Type/Length, private cache/nosniff, 401 без токена, 404 другого аккаунта/отсутствующей обложки и удаление кэша при удалении аккаунта. Доказательства: [verification/cover-http.json](verification/cover-http.json). Изображения и аудиофайлы проверки остаются только в `.runtime/`.

Готовый `release/server/start-dev.ps1` проверен с копией JAR в отдельной папке: 6 PASS, включая localhost по умолчанию, другой порт, явный LAN и сохранение аккаунта/токена после немедленного принудительного перезапуска. Изначальная проверка выявила стандартную задержку записи H2 500 мс; launcher задаёт WRITE_DELAY=0, после чего сценарий проходит. Доказательства: [verification/server-launcher.json](verification/server-launcher.json). Это проверка конкретного перезапуска процесса, а не моделирование отказа накопителя.

## Ограничения этой проверки

PostgreSQL runtime, Docker Compose, Caddy/публичный HTTPS, резервное копирование и восстановление в этом окружении не запускались: Docker отсутствует. Телефон, Bluetooth, iOS/Android native playback, реальный мобильный офлайн/фоновый режим в этот отчёт не входят. Кнопки ServerView и первый Download+Resume проверены кодом и контрактом, но пользовательские действия в ServerView не автоматизированы в данном тесте. Независимые UI/аудиопроверки Desktop описаны в общем TEST_REPORT.md.

История теперь сохраняет исходную дату и стабильный eventId; версионный PUT защищает плейлист от устаревшей записи. Для старых клиентов без eventId/version остаются прежние ограничения. Нет push-синхронизации и общей модели распространения локальных удалений. Обложки PNG/JPEG извлекаются из настоящих тегов и выдаются через защищённый API; транскодирование сервером не реализовано. Подробности обмена и границы — [SYNC_INTEGRITY_AUDIT.md](SYNC_INTEGRITY_AUDIT.md). Это проверенная первая реализация, а не подтверждение готовности публичного сервиса к эксплуатации.
