# Перенос пользовательских данных Desktop

Данные новой версии хранятся отдельно от установленного приложения: `%LOCALAPPDATA%/AuralisData`. Старый профиль `%LOCALAPPDATA%/Auralis` совпадал с прежним каталогом установки, поэтому перед его обновлением необходимо закончить перенос. Перенос выполняется до создания `LibraryService`; ошибка должна прекращать запуск/обновление, а не приводить к открытию пустой библиотеки.

## API

```java
boolean copied = DesktopDataMigration.migrateIfNeeded(legacyRoot, newRoot);
```

`io.auralis.desktop.DesktopDataMigration` не зависит от запуска JavaFX. Возвращает `true` после публикации готового нового профиля. Возвращает `false`, если старой базы нет или новая база уже существует и проходит проверку схемы и SQLite `quick_check`. Пустая, повреждённая или недоступная новая база вызывает `IOException`, чтобы updater не посчитал перенос завершённым. Старый каталог не перемещается и не удаляется.

До переноса старое приложение должно быть закрыто: база копируется согласованно даже с WAL, но новые записи старого процесса после момента снимка не синхронизируются в уже перенесённый профиль. Updater должен проверять это до вызова CLI миграции и запускать установщик только при успешном коде завершения.

## Порядок действий

1. Проверяются раздельные каталоги, отсутствие готовой новой базы и существование старой. Получается межпроцессная блокировка в постоянном sibling-файле `.<newRoot>.migration.lock`.
2. Рядом с новым каталогом создаётся уникальный staging-каталог. Из read-only SQLite-подключения выполняется `VACUUM INTO` в staging. Не используется `immutable=1`, поскольку этот режим не подходит для чтения ещё не перенесённых из WAL изменений. Оригинальный DB-файл и WAL не копируются обычным файловым копированием.
3. Копируются пользовательские файлы с сохранением времён. Корневые каталоги `app`, `runtime`, `tools`, `installer`, `licenses`, исполняемые `.exe`, пакеты `.msi`/`.msp`, исходная `library.db` и её SQLite sidecars исключаются. Символические ссылки/выходы через ссылки требуют ручного переноса и вызывают явную ошибку; мигратор не проходит по ним.
4. Только в копии SQLite, одной транзакцией, перебазируются абсолютные пути внутри старого корня: `tracks.path`, `tracks.artwork`, `playlists.artwork`, `import_roots.path`, а также значения `settings.value`, целиком представляющие такой абсолютный путь. Префикс похожего соседнего каталога не считается вложенным путём. Внешние оригиналы и внешние обложки остаются на прежних путях. Идентификаторы треков, избранное, история, порядок плейлистов, параметры и настройки синхронизации сохраняются.
5. В скопированных проектах `*.auralis.json` версии 1 аналогично меняются только `clips[].source`. Исходный JSON не изменяется. Некорректный проект вызывает ошибку вместо молчаливой потери ссылок.
6. Проверяются SQLite `integrity_check` и `foreign_key_check`. Снимок закрывается в `journal_mode=DELETE`, так что для публикации не требуется отдельный WAL.
7. Готовый staging-каталог публикуется атомарным переименованием в новый корень на том же файловом томе. Непустой новый каталог без DB вызывает ошибку; его файлы не перезаписываются. Существующий пустой каталог можно заменить. При ошибке staging удаляется, старая библиотека остаётся доступной. После аварийного завершения до публикации может остаться незавершённый staging; он не открывается как новый профиль и не препятствует повторной попытке.

SQLite документирует `VACUUM INTO` как согласованный снимок живой базы, который сохраняет оригинал; неконтролируемое прерывание может оставить незавершённый output, поэтому публикация происходит отдельным последним действием. WAL является частью постоянного состояния: простое копирование одного DB-файла может потерять committed-записи. [SQLite VACUUM INTO](https://www.sqlite.org/lang_vacuum.html), [SQLite WAL](https://www.sqlite.org/wal.html).

Миграция не является фоновым двусторонним sync-процессом и не удаляет старый профиль после успеха. Требования к `ATOMIC_MOVE`, свободному месту и доступу к каталогам проверяются действительными файловыми операциями; ошибка оставляет updater без разрешения на установку.

## Проверки

18 октября 2026: **7 тестов, 0 ошибок, 0 пропусков**, только JUnit `@TempDir`. Реальный `%LOCALAPPDATA%` не читался и не изменялся этими тестами.

- Открытый writer с отключённым autocheckpoint и настоящими committed-записями в WAL: последние треки, настройки, история и избранное попадают в новый профиль; старые DB и WAL побайтово неизменны.
- Managed audio/artwork/import roots и проекты используют новые пути; внешние оригиналы и обложки неизменны; порядок плейлиста сохраняется; база успешно открывается повторно.
- Runtime, приложение, инструменты и установщик не копируются.
- Повторный вызов не заменяет готовую новую библиотеку; отсутствие старой базы не создаёт пустую новую.
- Повреждённая старая база, будущая схема, повреждённый проект, непустой target и пересекающиеся каталоги завершаются ошибкой без публикации DB.
- После исправления ошибочного источника повторная попытка завершается успешно.
- Пустая/повреждённая существующая новая база не позволяет обойти перенос.

```powershell
mvn -B -ntp -pl apps/desktop -am test '-Dtest=DesktopDataMigrationTest' '-Dsurefire.failIfNoSpecifiedTests=false'
```
